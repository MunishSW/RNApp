# Spec diff: 001 (tdd-spec-generator) vs 002 (vanilla speckit)

Same BRD, same Figma node 2:937, same screen. Only the spec method differs.

- **001** = `specs/001-nonlogged-home-screen` (TDD skill v3.0.4)
- **002** = `specs/002-non-logged-in-home-page` (vanilla speckit)

## 1. One-line verdict

Both specs describe the same product. 001 has a **test-case spine**: QA case → task → FR → test → coverage report, each link machine-checkable. 002 has a **requirement spine** (FR/BR/scenario → task → test file) with no QA case list at all. 002 is traceable, but cannot answer "is every QA case covered?".

## 3. The core differences

### 3.1 Acceptance contract
- 001: QA workbook Sheet2 (71 cases) is the contract. Copied to `qa-cases.json` with id, desc, expected, type, approach (unit-testable vs manual), story.
- 002: contract is the BRD scenarios (P-/N-/E-). **No QA case list exists.**
- Dangling IDs: 002's tasks cite `TC-101…TC-808` (25 mentions in `tasks.md`, 1 in `manual-checks.md`) and test files carry `// Covers: … TC-301`. These IDs are defined **nowhere** in the folder: not in spec, research, or a JSON. They look invented or lifted from a source not saved. They are unverifiable.

### 3.2 Test-case coverage table
- 001 `tasks.md` ends with `## TC → Task coverage`: 71 rows, `TC id + description | Task(s) | Test approach | Story`, plus a counts line (71 · 65 unit · 6 manual).
- 002 has none. Closest is `checklists/traceability.md`, which is keyed on **FR**, not TC.

### 3.3 FR → TC back-link in spec
- 001 `spec.md` has `### Test-case → FR traceability`: a table FR → QA cases, **generated** from the tasks table (TC → task → task `Maps` FR). Closes the loop spec ↔ tasks.
- 002 spec has FR → scenarios (P/N/E) only.

### 3.4 Task format
- 001: each task has `**Maps**: FR-… · **Accept**: … · **Story**: BHFL-001`. Tests are written **with** the code in the same task (no Red-Green phases, per skill). Header says every test carries `// Covers: <TC-ID>`.
- 002: classic speckit layout. Per user story: "Tests (write first, confirm they fail)" then "Implementation". Tests are separate tasks (T019–T025) from code (T026–T035). IDs in trailing parentheses, no `Maps/Accept`.
- Result: 002 is real test-first TDD structure but **requirement-driven**. 001 is **case-driven**, tests and code per task.

### 3.5 Test marker
- 001: `// Covers: HOME_LAYOUT_TC_001` (QA ID only). The coverage tool greps it.
- 002: `// Covers: FR-4.5-03, N-05, TC-306 - description`. Mixed FR + scenario + TC. 122 markers in 22 files. Good volume, but the tool cannot map to a QA case because there is no `qa-cases.json`.

### 3.6 Coverage report
- 001: generated by `tools/coverage-report.js` from an actual scoped run. Sections: Summary, Input QA cases (71), Tests added (283), Pre-existing tests, Manual. Result: 67/71 automated, 4 manual, 0 gap.
- 002: none. Tasks are ticked `[X]` and manual checks are "NOT RUN", but nothing proves per-requirement coverage.

### 3.7 Manual / non-unit-testable
- 001: `manual-verification.json` maps TC → why manual. Flagged in coverage report "Action needed".
- 002: `manual-checks.md` table M-10..M-13 + `quickstart.md` M-1/M-2. Good content, not machine-readable, not tied to QA IDs.

### 3.8 Provenance and audit
- 001: `stories.json` timeline + `.tdd-ledger/` with 7 rounds of snapshots and signed tokens. `tdd-verify` can audit it.
- 002: none. Git history only.

### 3.9 Scope and decisions (not a method gap, but affects conversion)
- 001 excludes Sheet1 (202 other-module cases) and uses QA-resolved decisions (e.g. 300 ms tap, Skip/Update, no snooze noted).
- 002 differs on several decisions: PERF-4 = **200 ms** (001: 300 ms), version 401 shows **no popup** (001: message + Okay + logout), Pay Now has **no WebView** (001: WebView route stub), 002 is a deliberate **duplicate** feature folder (`nonLoggedInHome/` vs `nonLoggedHome/`). A converted 002 must keep its own decisions; do not "fix" it to 001.

## 4. What 002 does better (keep it)

- Per-endpoint `contracts/` (6 files) and `data-model.md`, `research.md`.
- FR IDs mirror BRD sections (FR-4.5-03), so BRD traceability is direct.
- Scenario IDs (P/N/E) tie every FR to a BRD scenario; `traceability.md` has BR/TV/PERF rows.
- Explicit Clarifications log with owner overrides of the BRD.

Conversion must **add** the TC spine on top and keep these.

## 5. What cannot be converted (be honest)

- `.tdd-ledger/` timestamps: tool says never hand-write. A converted spec gets a ledger starting **now**, marked as a retrofit, not back-dated.
- The real QA workbook: if the 002 team had QA cases, the file must be supplied. If none exist, TC IDs must be **derived from BRD scenarios (P/N/E) and labelled derived**, not passed off as QA-authored.
- Coverage numbers need a real jest run; cannot be written by hand.

## 7. Suggested next step

Run the conversion as a **staged vibe prompt on a copy**, checking each gate before the next:

1. G1+G2 (build `qa-cases.json`, resolve TC IDs) — human review, since it decides what "acceptance" means.
2. G3+G4+G5+G10 (tables, task format) — mechanical.
3. G6+G7 (markers, manual JSON) — mechanical.
4. G8+G9 (stories, coverage report) — tool-run, ledger starts as retrofit.

Then the stable prompt sequence becomes the skill (`tdd-retrofit`?). Open question for the team: does a 002-era QA workbook exist? If yes, G1 is trivial. If no, "derived from BRD" must be an explicit mode in the skill.
